# Fase 1 — Requisitos y trazabilidad

**Convención:** RF = requisito funcional; RNF = requisito no funcional. Los criterios de aceptación son comprobables y se convertirán en pruebas dentro de las fases de implementación. `F01–F16` remite a las 16 fases del Documento Maestro, no implica autorización para ejecutarlas.

## Requisitos funcionales

| ID | Requisito | Criterio de aceptación comprobable | Trazabilidad (sección del maestro) | Fase | Prueba prevista |
|---|---|---|---|---|---|
| RF-001 | La plataforma web permitirá crear cuenta con correo, contraseña, tipo de usuario y aceptación de condiciones aplicables. | Al enviar datos válidos se crea una cuenta pendiente de verificar; correo inválido, duplicado o contraseña no válida se rechazan con explicación en español. | §5, §8, §29 | F03 | API + integración de registro |
| RF-002 | La plataforma permitirá autenticación con Google mediante OAuth 2.0/OIDC. | Flujo exitoso inicia sesión o completa registro; cancelación, error del proveedor y cuenta duplicada no crean sesión inválida. | §5.2, §8, §29 | F03 | Integración OIDC mock y casos de fallo |
| RF-003 | El sistema permitirá vincular correo y Google a una cuenta existente de forma segura. | Solo una sesión ya autenticada y una verificación válida pueden vincular; identidad asociada a otra cuenta no se fusiona silenciosamente. | §5.2, §8 | F03 | API de vinculación, pruebas negativas |
| RF-004 | El usuario podrá reanudar el registro incompleto. | Al regresar autenticado se informa el paso pendiente y los documentos que requieren corrección; no se marca la cuenta verificada automáticamente. | §5.3, §6 | F04 | Prueba de persistencia de borrador |

| RF-006 | El sistema permitirá enviar solicitudes de verificación y documentos, con estados y revisión humana. | Se puede crear solicitud, revisar, solicitar corrección, verificar, rechazar con motivo o suspender; cada cambio queda auditado. | §6, §23 | F04 | API y transición de estados |
| RF-007 | El sistema apoyará revisión documental con IA intercambiable, sin decisión autónoma de riesgo. | Mock extrae/propone datos claramente identificados; casos dudosos requieren revisión humana; respuesta guarda confianza, explicación, versión y auditoría. | §7, §17, §28 | F04 / después del MVP para IA real | Pruebas de puerto, mock y revisión humana |

| RF-011 | La pantalla inicial permitirá elegir el perfil/intención y consultar condiciones, privacidad y ayuda. | Un usuario puede iniciar sesión o registro desde cada opción; textos y navegación funcionan en anchos móviles y escritorio. | §4 | F08 | Prueba de widgets responsive |
| RF-012 | El sistema mostrará un inicio diferente según perfil y estado de la cuenta. | Cada rol ve las acciones pertinentes y los recuentos corresponden a datos persistidos, no valores inventados. | §9, §24 | F08 | Widget/API por rol |
| RF-013 | Una empresa podrá crear una carga en cinco pasos: ruta, mercancía, vehículo, condiciones y revisión/publicación. | No se publica si faltan campos obligatorios; se puede volver y corregir; las condiciones identifican pagador según decisión provisional. | §10 | F06 | Flujo UI/API y validación |
| RF-014 | El sistema permitirá consultar cargas y filtrar por atributos disponibles. | Los filtros aplicados restringen correctamente resultados; estado vacío y error de red tienen mensajes útiles. | §11 | F06 | Prueba de búsqueda y filtros |
| RF-015 | Un usuario autorizado podrá crear ofertas y consultar la negociación. | Oferta y cambios de propuesta conservan actor, fecha e historial; contacto directo permanece oculto antes de contratación confirmada. | §12, §19 | F06 | Pruebas API y control de contacto |
| RF-016 | La contratación se completará solo tras todos los pasos y confirmaciones válidas. | Transición a contratada ocurre una sola vez; aceptación simultánea produce un único ganador y una respuesta de conflicto clara al resto. | §12, §30 | F06 | Prueba concurrente de doble aceptación |
| RF-017 | La transportadora podrá gestionar conductores, vehículos, flotas y asignaciones permitidas. | Asignar requiere permisos y compatibilidad; un vehículo o conductor no queda en dos viajes activos simultáneos. | §13, §30, §31 | F05–F07 | Prueba de restricciones y asignación |
| RF-018 | Se podrán administrar múltiples vehículos y sedes, y representar viajes recurrentes como instancias separadas. | Las entidades no se mezclan entre sedes; cada ocurrencia recurrente mantiene estado e identificador propios. | §30, §31 | F05–F07; recurrentes posterior al MVP | Prueba de modelo y aislamiento |
| RF-019 | El sistema permitirá crear simulaciones de viaje inmutables para comparar plan y ejecución. | Cada simulación muestra etiqueta SIMULACIÓN, parámetros, fecha y procedencia; editar el plan no altera una simulación ya guardada. | §14, §17, §30 | F09–F10 | Prueba de inmutabilidad |
| RF-020 | La simulación de ruta y costos usará fuentes configurables o mocks claramente etiquetados. | Con proveedor no disponible, no se inventa ruta/costo; el usuario ve estado, origen y fecha del último dato válido. | §14–§16 | F09 | Pruebas con mock y fallo |
| RF-021 | El sistema permitirá registrar peajes configurables con fecha y procedencia. | Valores de ejemplo se marcan SIMULADO/ESTIMADO; ningún valor sin fuente se muestra confirmado. | §15–§16 | F09 | Pruebas de procedencia |
| RF-022 | Los costos y gastos podrán registrarse y compararse con estimaciones, sin procesar dinero. | El cálculo separa valor acordado, estimados, gastos reales y ajustes; no se produce transferencia ni saldo custodiado. | §16, §21 | F14 | Servicio de liquidación y límites |
| RF-023 | El seguimiento registrará ubicación autorizada y estado del viaje, considerando capacidades del navegador. | Sin permiso, contexto seguro o señal, la UI informa la limitación; cada ubicación indica hora/procedencia y no se presume rastreo en segundo plano. | §14, §15, §20, §28, aclaración web aprobada | F09, F13 | Pruebas de permiso/ubicación simulada |
| RF-024 | El sistema permitirá registrar evidencias de recogida/entrega, daños, faltantes e incidencias. | Evidencia queda vinculada al viaje con actor y fecha; una incidencia impide marcar cierre hasta completar el flujo requerido. | §20, §22, §30 | F13 | Integración de entrega/incidencia |
| RF-025 | Los participantes podrán consultar mensajes, avisos y notificaciones autorizados. | Solo los miembros autorizados acceden al espacio; permisos web para push son opt-in; falta de permiso no bloquea avisos dentro de la plataforma. | §19, §30 | F12 | API/permiso navegador/mock |
| RF-026 | El chat detectará e informará posibles intentos de compartir contacto directo antes de contratación. | Un patrón detectado genera advertencia y evento auditable; el detector no se presenta como infalible ni altera contrato automáticamente. | §19, anti-evasión del prompt final | F12 / posterior MVP según priorización | Pruebas de patrones y falsos positivos |

| RF-028 | El panel web administrativo permitirá revisar usuarios, verificaciones, reportes, parámetros y servicios externos conforme a permisos. | Usuario sin rol administrativo recibe denegación del backend; acciones sensibles exigen permiso y registran actor/fecha. | §23 | F15 | Pruebas de autorización/auditoría |
| RF-029 | El sistema generará reportes por perfil usando datos trazables. | Cada métrica puede rastrearse a registros fuente y distingue valores estimados de confirmados; exportación respeta permisos. | §24, §30–31 | F15 | Pruebas de agregados y permisos |
| RF-030 | La plataforma mostrará beneficios solo según reglas vigentes y acuerdos reales. | Beneficio sin regla configurada o acuerdo comercial no se promete; el historial explica por qué se asignó. | §18 | Posterior al MVP | Prueba de elegibilidad/mock |
| RF-031 | El usuario podrá consultar datos previamente cargados y registrar gastos sin conexión cuando sea viable. | La cola indica pendiente/no sincronizada; conflicto se muestra y resuelve según regla; acción legal o contratación no se confirma offline. | §20, §31, prompt final | F10/F13; avanzado posterior MVP | Prueba offline y conflicto |

## Criterio de trazabilidad

La identificación RF/RNF es estable. Cada requisito enlaza a sección del Documento Maestro, fase de desarrollo y prueba prevista. Si una decisión posterior altera alcance o criterio, debe registrarse en `docs/DECISIONES.md` y actualizar el requisito con historial verificable.
